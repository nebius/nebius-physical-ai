# Use FlashAttention 4 on RTX PRO 6000

[Workbench docs](../README.md) · [Guide index](README.md) · [FA4 evidence and restrictions](../flash-attention.md)

Run your own training or inference application on a Nebius RTX PRO 6000
Blackwell Server Edition GPU with the qualified FA4 dependency set. Build the
shared CUDA 13 base, rebuild your application on it, connect the model's
attention calls, then validate and deploy the resulting application image.

**Delivery status:** this integration provides a base recipe, a guarded import
adapter, GPU checks and full-model reference evidence. It does not publish a new
base-image digest or automatically update an application's container or backend.

For a standalone FA2 baseline and the optimized inference callable, follow the
[FA2/FA4 comparison guide](fa2-fa4-comparison.md). That path builds separate
images and measures the same real model in both; existing FA4-versus-SDPA results
do not establish a speedup over FA2. The [latest measured comparison](../fa4-rtx-optimization.md)
shows 1.07–2.08× FA2 on qualified attention calls, but less than 1% on complete
SDXL generation. The optimization remains opt-in and inference-only.

## Which container name should I use?

Use **`cuda13-blackwell`** for new base builds. The shared CUDA 13 recipe targets
RTX PRO 6000 (`sm_120`), B200 (`sm_100`) and B300 (`sm_103`). The family name
describes the build targets; it does not certify every workload on each GPU.

The historical `cuda13-b300` name remains a compatibility alias. The old `base/cuda13-b300/build.sh` forwards to the canonical build script;
Dockerfiles and validation scripts live in `base/cuda13-blackwell`. Each build tags the
same image with both prefixes and the same suffix. With `--registry`, both
registry names are tagged; with `--push`, both are pushed. Existing published
tags, digests and validation records retain their original identities. This
rename does not publish a new image.

Use **RTX PRO 6000 / FA4** to identify this adoption path. The container tag
identifies software; the workflow's GPU resource selection identifies hardware.
Select RTX PRO 6000 explicitly and require compute capability `12.0` in the
validation below. A result on RTX does not qualify this FA4 build on B200/B300.

| Layer | What to use | What it does |
| --- | --- | --- |
| Base recipe | [`base/cuda13-blackwell`](../../../npa/docker/workbench/base/cuda13-blackwell/README.md) | Provides CUDA, Torch, pinned FA4/CUTLASS/Quack, the root adapter and GPU checks |
| Local base image | `npa-base:cuda13-blackwell-dev-<full-source-sha>` | Build output; this name alone is not a registry artifact |
| Application image | Your rebuilt image, deployed by registry digest | Contains your model code, application dependencies and launch command |
| Execution | Your existing Workbench/SkyPilot workflow on RTX PRO 6000 | Runs the application image; installing a new host CLI does not change its Python environment |

## 1. Prepare the GPU build host

Use a Linux x86-64 Nebius GPU VM with Docker, NVIDIA Container Toolkit and a
compatible CUDA 13 driver. The recorded RTX runs used driver `580.173.02`.
Complete [Workbench setup](../getting-started.md) for your project and verify
provider authentication before provisioning:

```bash
npa workbench health preflight --checks nebius --json
```

Use a separate checkout at a committed revision containing the
[FA4 integration](https://github.com/nebius/nebius-physical-ai/pull/803) on that
host. Run the next commands from the repository root. A full Git SHA identifies the recipe;
retain the resulting image ID as well, because a new build is a new artifact.

## 2. Build the FA4 base

```bash
FA4_SOURCE_SHA="$(git rev-parse HEAD)"
FA4_BASE_IMAGE="npa-base:cuda13-blackwell-dev-${FA4_SOURCE_SHA}"
npa/docker/workbench/base/cuda13-blackwell/build.sh --tag "dev-${FA4_SOURCE_SHA}"
docker image inspect "$FA4_BASE_IMAGE" --format '{{.Id}}'
```

This builds locally on that Docker daemon. It does not push or promote an
image. The recipe selects CUDA 13.0.1, Torch 2.13.0/cu130, upstream FA4 commit
`eed1971f5132630dc296fe37601e834d4b57a248`, CUTLASS DSL 4.6.2 and Quack 0.6.4.
See [the pinned stack](../flash-attention.md#pinned-recipe-and-integration).

## 3. Rebuild your application image

Adapt your existing Dockerfile to accept the base as a build argument. The
excerpt below assumes a compatible Python application with `requirements.txt`.
Carry over your actual entrypoint, system packages and scheduler bootstrap;
the base alone is not a complete application or a SkyPilot bootstrap image.
Keep credentials, checkpoints and datasets outside the build context and use
your existing runtime mounts or fetch steps for them.

Create `attention-constraints.txt` in your application's build context:

```text
torch==2.13.0+cu130
torchvision==0.28.0+cu130
torchaudio==2.11.0+cu130
nvidia-cutlass-dsl==4.6.2
quack-kernels==0.6.4
```

Append the exact FA4 distribution version from the selected base:

```bash
docker run --rm --network none --entrypoint python "$FA4_BASE_IMAGE" \
  -c 'from importlib.metadata import version; print("flash-attn-4==" + version("flash-attn-4"))' \
  >> attention-constraints.txt
```

Upstream's version includes a Git abbreviation that can lengthen as its
repository grows. The full source pin remains
`eed1971f5132630dc296fe37601e834d4b57a248`; the inference guard accepts only
abbreviations of that pin with the qualified public version.

Use these constraints for every later dependency installation so the resolver
fails on an incompatible requirement instead of replacing the qualified stack.
Do not install standalone `flash-attn` (FA2) alongside the base's root adapter;
resolve dependencies that require it before proceeding. Rebuild your own CUDA
extensions against the new Torch/CUDA stack with SM120 support.

```dockerfile
ARG FA4_BASE_IMAGE
FROM ${FA4_BASE_IMAGE}

USER root
WORKDIR /app
COPY requirements.txt attention-constraints.txt /app/
RUN python -m pip install -c attention-constraints.txt -r requirements.txt \
    && python -m pip check
COPY --chown=1000:1000 . /app
USER ubuntu
# Retain the application's existing ENTRYPOINT/CMD and scheduler bootstrap.
```

Save the adapted file as `Dockerfile.fa4`. From the application's directory, on
the same Docker daemon that holds the base image, build the candidate. Keep
`FA4_SOURCE_SHA` and `FA4_BASE_IMAGE` from step 2 in this shell:

```bash
FA4_APP_IMAGE="workload-rtx6000-fa4:dev-${FA4_SOURCE_SHA}"
docker build --build-arg "FA4_BASE_IMAGE=${FA4_BASE_IMAGE}" \
  -f Dockerfile.fa4 -t "$FA4_APP_IMAGE" .
docker image inspect "$FA4_APP_IMAGE" --format '{{.Id}}'
```

Also record the application's own source revision and dependency lock. The tag
above identifies the base recipe; it does not identify your application source.
The application image can have an RTX-specific name while its shared base keeps
the canonical `cuda13-blackwell` family name.

## 4. Select FA4 inside the model

Installing FA4 does not switch a model that selects SDPA or FA2. Use the explicit
CuTe namespace in the model's attention implementation, preserve its causal
behavior and scale, and use the qualified RTX settings:

```python
from flash_attn.cute import flash_attn_func

# q: [batch, query_tokens, query_heads, head_dim]
# k/v: [batch, key_tokens, kv_heads, head_dim]
# is_causal and scale come from the model's existing attention semantics.
result = flash_attn_func(
    q, k, v, causal=is_causal, softmax_scale=scale,
    pack_gqa=False, num_splits=1,
)
output = result[0] if isinstance(result, tuple) else result
```

This example is for a model that consumes only the attention output tensor.
Packed sequences need the named sequence metadata described in the
[API guidance](../flash-attention.md#pinned-recipe-and-integration). FA2 and FA4
assign different meanings to positional arguments after Q/K/V.

The base's `from flash_attn import ...` adapter also calls FA4, but deliberately
accepts a restricted contract. It rejects unsupported options and never changes
backends after a failure. Do not remove required masks, dropout, normalization,
determinism or auxiliary outputs merely to make a call pass. The kernel
qualification covers FP16/BF16 and head dimensions 64/128; check all required
features against the [qualification scope](../flash-attention.md#qualification-scope).

For inference with the exact documented shapes and standard scale, use
[`make_inference_attention()`](fa2-fa4-comparison.md#experiment-with-fa4-inference-tiles)
to opt into cached kernel launches and measured tiles. That narrow callable
rejects gradients and advanced options; it does not automatically replace the
native example above. Qualify its outputs and measure cold and warm application
performance before enabling it. The comparison guide includes a persistent-cache
recipe and a public 125-check GPU qualification worker.

## 5. Validate the final application image on RTX

Run these checks after installing all application dependencies. The image's
UID 1000 must be able to write the results directory:

```bash
set -euo pipefail
mkdir -p fa4-results
sudo chown 1000:1000 fa4-results
for FA4_API in flash_attn.cute flash_attn; do
  docker run --rm --gpus all --network none \
    --user 1000:1000 --entrypoint python \
    --cap-drop ALL --security-opt no-new-privileges \
    --read-only --tmpfs /tmp:rw,exec,mode=1777 \
    -e HOME=/tmp -e CUDA_CACHE_PATH=/tmp/cuda-cache \
    -e TORCH_EXTENSIONS_DIR=/tmp/torch-extensions \
    -v "$PWD/fa4-results:/output" "$FA4_APP_IMAGE" \
    /npa/gpu_capability_smoke.py --expect-capability 12.0 \
    --attention-api "$FA4_API" --json-output "/output/${FA4_API}.json"
done
```

Require both commands to exit zero and both JSON reports to contain
`status: passed` and 24 passing cases. An import, successful build or a test of
only the parent base does not qualify the final application image.

Then run the actual model against its existing backend on the same RTX hardware.
Compare outputs, gradients, complete training/evaluation behavior, peak memory,
cold-start/JIT cost and repeated steady-state timings. Include the longest
sequences, batch sizes and single-node/distributed layouts you intend to use.
Inspect the workload's real output artifacts before accepting the change.

## 6. Deploy the accepted application image

Publish the validated application image to your authorized private registry
under its existing security and licensing process. Record the registry manifest
digest, source revisions, dependency versions and validation results. A local
Docker image ID is not a registry manifest digest.

Update the **application image reference** in your existing Workbench/SkyPilot
workflow to that immutable digest and explicitly select RTX PRO 6000 capacity.
Retain the workflow's application command, storage/identity configuration and
required container bootstrap. Follow [workflow submission](../npa-workflow-guide.md)
and [SkyPilot setup](../../orchestration/skypilot-setup.md) for that runtime's
image and scheduling requirements. Keep the previous image digest for rollback.

FA4 remains a per-model choice. New base builds include the updated dependency;
existing published images and model backend choices do not change automatically.
Stop completed validation jobs and remove task-owned compute and disks using
the [teardown procedure](../../teardown.md).

## Evidence and boundaries

The [fresh base qualification](../flash-attention.md#root-adapter-safety-qualification-2026-09-28)
passed 48 output/gradient cases across native FA4 and the guarded adapter. The
separate [SDXL report](../fa4-sdxl-validation.md) includes 24 complete image
generations, real rendered PNGs, kernel evidence and mixed performance results.

Those records establish the documented base/API and reference-model behavior.
They do not validate this illustrative application Dockerfile or an arbitrary
private model. This guide adds the adoption steps, not a new published image,
an automatic performance selector or a change to GPU interconnects.
